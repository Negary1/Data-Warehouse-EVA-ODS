
# 1. Project Title
## Analysis of Agricultural Productivity and Land Use to Support Food Security in Colombia

## 1.1. Selected SDG

The selected Sustainable Development Goal (SDG) is SDG 2: Zero Hunger.

This project is related to SDG 2 through the analysis of agricultural production, land use, and crop productivity in Colombia. The objective is not to directly measure hunger, since the EVA dataset contains information about agricultural production, but rather to analyze productive factors that can contribute to food availability and the stability of agricultural systems.

## 1.2. Colombian Problem

There are significant differences in the way agricultural land is used and in the productivity obtained between Colombian territories and crops. A municipality may have a large amount of planted or harvested land without necessarily obtaining a proportionally high level of production. Similarly, some crops may occupy significant areas of land while presenting lower yields compared with other territories or with their own historical performance.

This situation makes it difficult to identify where opportunities exist to improve the productive use of agricultural land, particularly for crops relevant to food supply.

Therefore, this project proposes analyzing the relationship between:

- Planted area.
- Harvested area.
- Agricultural production.
- Agricultural yield.
- Crop type and characteristics.
- Municipality and department.
- Evolution during the 2019–2025 period.

### Geographic Scope

Since the dataset provides national coverage, the initial analysis will cover Colombia, with a detailed analysis at the following territorial levels:

**Department → Municipality**

This approach allows territorial comparisons and the identification of differences between municipalities and departments without limiting the project to a single department.

### Sectoral Scope

The analysis will focus on the agricultural sector, specifically on the crops registered in the Municipal Agricultural Evaluations (EVA).

To maintain a clear relationship with SDG 2, crops with greater relevance to agricultural production and food availability may subsequently be prioritized or classified. However, all agricultural records will initially be retained during the exploration and profiling stages so that any subsequent selection is supported by the data rather than by an anticipated decision.

### Problem Statement

 The territorial and temporal variability in the productive use of agricultural land and crop yields across Colombian municipalities makes it difficult to identify gaps and opportunities for improving productive efficiency and strengthening food availability. Through the analysis of Municipal Agricultural Evaluations (EVA) from 2019 to 2025, this project seeks to identify territories, crops, and productive patterns that can support decision-making aimed at achieving more efficient and sustainable agriculture, in alignment with SDG 2: Zero Hunger.

# 7. Data Profiling and Quality Assessment

Data profiling was conducted systematically using a series of custom Python scripts (numbered 01 through 08), designed to progressively analyze the structural, semantic, and physical characteristics of the dataset in preparation for the Data Warehouse design.


## 7.1. Dataset Dimensions
The source dataset contains a total of 166,732 rows and 18 columns. Data quality checks confirmed 0 null values, 0 empty strings, and 0 exact physical duplicate records across the entire dataset.

## 7.2. Column Names and Data Types
The dataset's 18 attributes are organized into four functional groups:

*   **Geographic attributes:** Department code, department name, municipality code, municipality name.
*   **Agricultural attributes:** Crop group, subgroup, crop, crop disaggregation, scientific name, crop cycle, physical state.
*   **Temporal attributes:** Year, period, period type, semester.
*   **Metric attributes:** Planted area, harvested area, production, yield.


## 7.3. Missing Values & Exact Duplicates
Initial diagnostics, executed through `01_exploracion_inicial.py`, confirmed the absence of data quality issues at the structural level: 0 null values, 0 empty strings, and 0 exact physical duplicate records were found across all 166,732 rows.


## 7.4. Unique Values and Cardinality
*   **Geographic Cardinality:** The dataset spans 32 departments and 1,103 unique municipal DANE codes, but only 1,021 unique municipality names, with 64 names repeated across different codes.
*   **Agricultural Cardinality:** The dataset contains 8 crop groups, 23 subgroups, 165 crops, 194 crop disaggregations, 194 crop codes, and 158 scientific names, along with 2 crop cycles and 10 physical states. A strict 1:1 correspondence exists between crop codes and crop disaggregations.

## 7.5. Temporal and Geographic Coverage
The dataset covers the period from 2019 to 2025, comprising 21 distinct periods (7 annual and 14 semester-based). Geographically, it spans 1,103 municipalities across 32 departments, providing consistent municipal-level coverage throughout the full temporal range.

## 7.6. Semantic Analysis and Business Rules
Semantic validation was performed through `03_analisis_semantico.py`, along with its complementary scripts `03_1` and `03_2`, to verify business rules and detect semantic anomalies within the dataset:

*   **Mathematical Consistency:** The formula $\text{Yield} = \frac{\text{Production}}{\text{Harvested Area}}$ was proven to be 100% consistent across all valid records.
*   **Temporal Logic:** The analysis proved that the 'Annual' period represents an independent observation within the dataset and cannot be calculated as the simple sum of Semester A and Semester B values.


## 7.7. Invalid or Suspicious Values
The semantic analysis identified 13,208 records where Harvested Area exceeds Planted Area, with 99.96% of these cases occurring in transient crops. This pattern appears massively starting in 2022, corresponding to a documented methodological change rather than a data quality defect.

Additionally, zero-value patterns were validated as legitimate operational scenarios rather than missing data: 7,112 records show Planted Area greater than zero with zero values in other metrics, and additional cases were validated where Planted Area equals zero while Harvested Area is greater than zero.

## 7.8. Descriptive Statistics and Formatting Issues
The initial profiling scripts, `01_exploracion_inicial.py` and `02_perfilamiento_dataset.py`, identified two key formatting issues requiring correction during transformation:

*   DANE geographic codes (`codigo_departamento`, `codigo_municipio`) load as integers by default, resulting in the loss of leading zeros.
*   Metric fields use localized numeric formatting with commas, such as `9.217,00`, requiring standardization to a decimal-point format.

## 7.9. Physical Staging Profiling
Physical profiling was conducted on the transformed staging data through `07_perfilamiento_fisico_staging.py`. This script defined the exact physical constraints required for the Data Warehouse schema, including maximum `VARCHAR` lengths for text fields and appropriate `DECIMAL` precision and scale for numeric metrics.

## 7.10. Historical Dimensional Stability (SCD Analysis)
Historical stability was analyzed using `08_validacion_historica_dimensiones.py`, which examined the geographic and crop dimensions across the full 2019–2025 timeframe. The analysis concluded that there are zero historical variations in geographic or crop attributes over this period, confirming that Slowly Changing Dimensions (SCD Type 2) are not required for this dimensional model.

# 9. Data Preparation Strategy

### 9.1. Data Type Conversion and Standardization
Agricultural metrics (`area_sembrada`, `area_cosechada`, `produccion`, `rendimiento`) originate as strings following localized Colombian numeric formatting, using commas for decimals and dots for thousands separators (e.g., "9.217,00"). The staging script converts these string-formatted metrics into standard numeric floating-point/decimal values (e.g., 9217.00), enabling accurate mathematical operations in downstream analytical processing.

### 9.2. Missing Value Handling
The profiling phase confirmed that the dataset contains 0 native NULLs and 0 empty strings. A strict semantic rule was applied to zero values: zeros (0) are treated as valid, real-world observations rather than missing data. For example, a planted area greater than zero combined with a harvested area of zero indicates a crop failure or lost cycle, not a data quality issue. Accordingly, zeros are deliberately not converted to NULLs during staging.

### 9.3. Duplicate Analysis and Treatment
The dataset natively contains 0 exact row duplicates. The validation script `06_validacion_staging.py` asserts uniqueness at the defined natural grain (`codigo_municipio` + `codigo_cultivo` + `anio` + `periodo`). Since no duplicates exist at this grain, no aggressive deduplication or row deletion was required during the staging phase.


### 9.4. Date Parsing and Standardization
The dataset does not follow a standard daily date format (YYYY-MM-DD), relying instead on years and agricultural periods. The `anio` column is cast to integer type, while the `periodo` column is preserved exactly as a string (e.g., '2019', '2024A', '2024B'). A strict business rule dictates that annual periods are independent observations and are not automatically calculated or aggregated as the sum of Semester A and Semester B.


### 9.5. Categorical Harmonization
Descriptive text fields require basic standardization without altering their semantic meaning. Fields such as `departamento` and `municipio` undergo basic text standardization, including the stripping of leading/trailing whitespace and casing normalization, to prevent the accidental creation of duplicate dimension entries later in the pipeline.


### 9.6. Identifier and Text Standardization
DANE geographic codes (`codigo_departamento`, `codigo_municipio`) must be preserved exactly as they appear in the source. These identifiers are explicitly cast and handled as strings (`VARCHAR`) rather than integers, preventing the loss of crucial leading zeros (e.g., '05001' becoming '5001'), which would otherwise break geographic joins in the Data Warehouse.


### 9.7. Invalid and Inconsistent Value Handling
Profiling revealed cases where `area_cosechada` exceeds `area_sembrada` (Harvested Area greater than Planted Area), heavily concentrated in temporary crops starting in 2022. Due to a confirmed methodological change in the source data collection process that year, this condition is treated as a valid historical anomaly rather than an error. The staging script preserves these records as-is, without applying automatic deletion or correction. Negative values for metrics are strictly validated to ensure they do not exist in the dataset.


### 9.8. Derived Attributes
The staging phase avoids aggressive semantic modifications, preferring to keep the raw representation intact for the Data Warehouse. As a result, no major derived attributes are created in the immediate staging table (`eva_agricola_staging.csv`). However, the foundation is laid for deriving time-based classifications, such as `tipo_periodo` ('Anual' vs. 'Semestral'), which are explicitly handled during the Dimensional Data Model loading phase.


# 10. Fact Table Grain

## 10.1. Grain Definition
The granularity of the central fact table (`fact_produccion_agricola`) is defined at the most detailed atomic level observed in the dataset. *A single row in the fact table represents one agricultural observation of a specific crop, in a specific municipality, for a specific period of a given year.*

### Business Grain (Natural Keys)
The unique observation is identified in the source data by the combination of four natural attributes:
*   `codigo_municipio` (Municipality Code)
*   `codigo_cultivo` (Crop Code)
*   `anio` (Year)
*   `periodo` (Period, e.g., '2024', '2024A', '2024B')

### Physical Grain (Surrogate Keys)
In the Data Warehouse dimensional model, this grain is physically protected by a composite unique constraint (`uk_fact_grain`) on the following surrogate keys:
*   `sk_geografia`
*   `sk_cultivo`
*   `sk_tiempo`

### Analytical Justification
During the Data Profiling phase (Phase 4 - Granularity), this hypothesis was formally validated. The combination of municipality, crop code, year, and period yielded exactly 166,732 unique combinations for the 166,732 records in the dataset, confirming there are zero duplicates at this level. Furthermore, it was determined that adding lower hierarchical levels, such as crop breakdown (`desagregacion_cultivo`), did not provide additional uniqueness because it holds a strict 1:1 relationship with the crop code (`codigo_cultivo`).

This schema centers on a single fact table, `fact_produccion_agricola`, surrounded by three denormalized dimension tables: `dim_geografia`, `dim_cultivo`, and `dim_tiempo`. This structure minimizes join complexity and supports efficient aggregation across geographic, crop-related, and temporal perspectives.

## 11.4. Surrogate Keys
Surrogate keys (`sk_geografia`, `sk_cultivo`, `sk_tiempo`) are auto-generated integers created by the Data Warehouse, independent of any source-system identifier. Their purpose is to isolate the DW from changes in the source systems, ensuring that modifications to source codes or naming conventions do not impact the integrity of historical fact records.

## 11.5. Primary Key and Foreign Key Relationships
The fact table `fact_produccion_agricola` acts as the center of the Star Schema. Each foreign key in the fact table (`sk_geografia`, `sk_cultivo`, `sk_tiempo`) maps directly to the corresponding primary key in its respective dimension table (`dim_geografia`, `dim_cultivo`, `dim_tiempo`). This structure resolves the many-to-many relationships between observations and their descriptive contexts, allowing each fact row to be enriched with geographic, crop, and temporal attributes through simple join operations.

## 11.6. Analytical Justification of the Dimensional Model
*   **Geography:** The DANE municipality code (`codigo_municipio`) is treated as the true identifier of a municipality, not its name. Data profiling revealed 1,103 distinct municipality codes but only 1,021 distinct municipality names, with 64 names shared across multiple codes. Consequently, codes are preserved as text/string fields to avoid ambiguity in geographic identification.
*   **Crop:** The scientific name (`nombre_cientifico`) does not uniquely identify a crop, as profiling showed 194 distinct crop codes against only 158 distinct scientific names. For this reason, `nombre_cientifico` is retained strictly as a descriptive attribute rather than a unique identifier. In contrast, `codigo_cultivo` and `desagregacion_cultivo` maintain a 1:1 relationship, reinforcing their role as reliable identifiers within the crop hierarchy.
*   **Time:** The annual period is treated as an independent observation within the dataset and cannot be derived by summing Semester A and Semester B values, due to differences in agricultural reporting logic between annual and semester-based measurements. The time dimension is therefore designed to accommodate distinct, non-additive periods such as "2024" (Annual), "2024A" (Semester A), and "2024B" (Semester B).
*   **Measures:** Instances where `area_cosechada` exceeds `area_sembrada` are retained as mathematically valid, resulting from a significant methodological change in reporting starting in 2022, which predominantly affected temporary crops. Despite this anomaly, `rendimiento` continues to follow a strict mathematical relationship, calculated as `produccion` divided by `area_cosechada`.
*   **Historical Stability (SCD):** A dedicated historical validation, executed through `08_validacion_historica_dimensiones.py`, analyzed the stability of the attributes within the Geography (`dim_geografia`) and Crop (`dim_cultivo`) dimensions across the full 2019–2025 period. The analysis found zero historical variations in these attributes over that timeframe. Based on this finding, it was concluded that a Slowly Changing Dimension (SCD Type 2) strategy is not required for the current dimensional model, as the underlying geographic and crop attributes have remained fully stable throughout the observed history.

# 14. ETL Pipeline

The ETL pipeline is implemented in Python as a modular sequence of numbered scripts, leveraging Pandas for extraction, profiling, and transformation, together with SQLAlchemy and PyMySQL for connecting to and loading data into the MySQL target database. Schema definitions follow pure DDL SQL.

## 14.1. Extract
Extraction is handled by `04_extraccion.py`, which reads the official EVA dataset — containing 166,732 rows and 18 attributes — using Pandas' `pd.read_csv` function, and stores it in the RAW zone without any semantic modifications. A critical design decision at this stage is the explicit import of geographic and crop identification codes — `codigo_departamento`, `codigo_municipio`, and `codigo_cultivo` — as string/text type (`dtype=str`). This prevents the loss of leading zeros that would otherwise occur if these codes were interpreted as integers (for example, preserving department code '05' instead of it being converted to the integer 5). During the initial exploratory phase, chunk-based reading was used to manage the file volume efficiently.

## 14.2. Transform — Data Preparation
Data preparation is handled by `05_transformacion_staging.py`, which performs transformations in memory using Pandas DataFrames, generating a persistent CSV Staging Area file as an intermediate validation layer prior to loading into the Data Warehouse. This script renames columns, casts DANE codes to string type, converts localized string metrics to decimals, and standardizes text. The data cleaning and standardization process includes:

*   **Metric Conversion:** Localized Colombian decimal strings (using commas and dots, e.g., '9.217,00') are converted into standard numeric float/decimal values.
*   **Text Harmonization:** Department and municipality text names are standardized for consistency.
*   **Quality Rules:** Zero values in metric fields are preserved as valid observations rather than converted to NULL, since they represent real-world scenarios (e.g., a planted area greater than zero with a harvested area of zero).
*   **Methodological Integrity:** Records where harvested area exceeds planted area — resulting from a significant methodological shift starting in 2022 affecting temporary crops — are kept as informative rather than corrected or deleted.

The script enforces strict record-count integrity: no records are deleted, and no records are added during transformation.

## 14.3. Transform — Dimensional Transformation
Dimensional transformation is handled by `09_carga_dw.py`, which connects to MySQL via SQLAlchemy, reads the staging data, creates the DB schema, and transforms the cleaned data into the three dimension tables: `dim_geografia`, `dim_cultivo`, and `dim_tiempo`.

*   **Time Dimension Logic:** Annual observations (e.g., '2024') are kept separate from semester observations (e.g., '2024A', '2024B'), since annual metrics are independent reports rather than simple sums of Semester A and Semester B.
*   **Surrogate Key Lookup & Assignment:** Surrogate Keys (SKs) are generated by MySQL using `AUTO_INCREMENT`. The script first loads the dimension tables, allowing MySQL to generate the SKs, then builds in-memory lookups mapping natural business keys (`codigo_municipio`, `codigo_cultivo`, `periodo`/`anio`) to their corresponding surrogate keys. This mapping is used to assemble the `fact_produccion_agricola` table with the correct foreign key references.

## 14.4. Validate
Validation is handled by two dedicated scripts:

*   **`06_validacion_staging.py`:** Validates volume, structure, data types, nulls, temporal consistency, and unique granularity. This includes mathematical validation — verifying that `rendimiento` strictly adheres to the rule `rendimiento = produccion / area_cosechada`, confirming 100% consistency across all evaluable records — and granularity validation, confirming uniqueness at the candidate grain defined by `codigo_municipio` + `codigo_cultivo` + `anio` + `periodo`, with 166,732 unique entries and zero duplicates.
*   **`07_perfilamiento_fisico_staging.py`:** Analyzes physical traits of the staging data, such as `VARCHAR` lengths and `DECIMAL` precision, to dictate the physical schema of the Data Warehouse.

## 14.5. Load
Loading is handled by `09_carga_dw.py`, following an Initial Full Load strategy (Truncate and Load), designed for development purposes and full execution reproducibility. The script recreates/truncates the tables in MySQL, transforms and loads the dimension tables first so that surrogate keys are auto-generated, then uses the resulting in-memory lookups to transform and load the `fact_produccion_agricola` table with the resolved surrogate key mappings.

# 15. Data Warehouse

## 15.1. Database Technology
The Data Warehouse is built on MySQL 8.0, using the InnoDB storage engine to ensure ACID compliance, transactional integrity, and full support for foreign key constraints. The database, named `dw_eva_agricola`, uses the `utf8mb4` character set with `utf8mb4_0900_ai_ci` collation, enabling correct storage and comparison of special Spanish characters present in geographic and agricultural text fields.

Connectivity and data management are handled programmatically from Python, using SQLAlchemy (`create_engine`) in combination with the `mysql+pymysql` driver (PyMySQL) to establish and manage the database connection.

## 15.2. Data Warehouse Structure
The Data Warehouse follows a classic Star Schema architecture, consisting of three dimension tables surrounding one central fact table:

| Table | Type | Row Count | Description |
| :--- | :--- | :---: | :--- |
| `dim_geografia` | Dimension | 1,103 | Unique municipal records |
| `dim_cultivo` | Dimension | 194 | Unique crop classification records |
| `dim_tiempo` | Dimension | 21 | Distinct reporting periods (7 annual, 14 semestral) |
| `fact_produccion_agricola` | Fact | 166,732 | Agricultural observations at the municipal/crop/period level |

## 15.3. Schema Creation
The schema is created via the DDL script `sql/01_crear_esquema_dw.sql`, which defines all four tables of the Star Schema:
```sql
CREATE TABLE dim_geografia (
    sk_geografia INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    codigo_departamento VARCHAR(2),
    departamento VARCHAR(100),
    codigo_municipio VARCHAR(5),
    municipio VARCHAR(100),
    UNIQUE KEY (codigo_municipio)
);

CREATE TABLE dim_cultivo (
    sk_cultivo INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    codigo_cultivo VARCHAR(7),
    grupo_cultivo VARCHAR(100),
    subgrupo VARCHAR(100),
    cultivo VARCHAR(100),
    desagregacion_cultivo VARCHAR(100),
    nombre_cientifico VARCHAR(100),
    ciclo_cultivo VARCHAR(20),
    UNIQUE KEY (codigo_cultivo)
);

CREATE TABLE dim_tiempo (
    sk_tiempo INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    anio SMALLINT UNSIGNED,
    periodo VARCHAR(5),
    tipo_periodo VARCHAR(20),
    semestre CHAR(1) NULL,
    UNIQUE KEY (periodo)
);

    CREATE TABLE fact_produccion_agricola (
        sk_produccion_agricola INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
        sk_geografia INT UNSIGNED,
        sk_cultivo INT UNSIGNED,
        sk_tiempo INT UNSIGNED,
        area_sembrada DECIMAL(7,2) CHECK (area_sembrada >= 0),
        area_cosechada DECIMAL(7,2) CHECK (area_cosechada >= 0),
        produccion DECIMAL(9,2) CHECK (produccion >= 0),
        rendimiento DECIMAL(5,2) CHECK (rendimiento >= 0),
        CONSTRAINT fk_fact_geografia FOREIGN KEY (sk_geografia) REFERENCES dim_geografia(sk_geografia),
        CONSTRAINT fk_fact_cultivo FOREIGN KEY (sk_cultivo) REFERENCES dim_cultivo(sk_cultivo),
        CONSTRAINT fk_fact_tiempo FOREIGN KEY (sk_tiempo) REFERENCES dim_tiempo(sk_tiempo),
        CONSTRAINT uk_fact_grain UNIQUE (sk_geografia, sk_cultivo, sk_tiempo)
    );
```
## 15.4. Dimension Loading
Dimension tables are loaded directly from `data/staging/eva_agricola_staging.csv` using Python, leveraging Pandas and the `to_sql` method with batch inserts (`chunksize = 1000`).

*   **`dim_geografia`:** Deduplicated by `codigo_municipio`, resulting in 1,103 rows.
*   **`dim_cultivo`:** Deduplicated by `codigo_cultivo`, resulting in 194 rows.
*   **`dim_tiempo`:** Derived from unique `periodo` values, extracting `anio`, `tipo_periodo` ('Anual' vs 'Semestral'), and `semestre` ('A', 'B', or NULL), resulting in 21 rows.

In all three cases, surrogate keys (`sk_*`) are omitted during insertion and are automatically generated by MySQL's `AUTO_INCREMENT` mechanism.

## 15.5. Fact Table Loading
Loading the fact table requires resolving natural business keys into Data Warehouse surrogate keys. This is accomplished through memory-efficient lookup tables: `codigo_municipio` -> `sk_geografia`, `codigo_cultivo` -> `sk_cultivo`, and `periodo` -> `sk_tiempo`.

Staging data is joined with these dimension lookups using Pandas left joins, validated with the `validate="many_to_one"` parameter to ensure correct cardinality. Measures (`area_sembrada`, `area_cosechada`, `produccion`, `rendimiento`) are rounded to 2 decimal places before insertion. The resulting fact records are then loaded into MySQL in batches of 5,000 rows (`chunksize = 5000`).


## 15.6. Referential Integrity
Referential integrity is enforced at two levels:

*   **Database Level:** Physical foreign key constraints (`fk_fact_geografia`, `fk_fact_cultivo`, `fk_fact_tiempo`) ensure valid references between the fact table and its dimensions. A composite unique index (`uk_fact_grain`) protects the grain of the fact table by preventing duplicate combinations of `sk_geografia`, `sk_cultivo`, and `sk_tiempo`. Numeric `CHECK` constraints guarantee non-negative values across all measures.
*   **Application Level:** Automated Python validation queries execute direct SQL checks after each load to confirm: zero orphaned foreign keys, zero NULL surrogate keys, exact grain uniqueness, and an exact total of 166,732 rows in the fact table.

# 16. Analytical Queries and KPIs

To map each business requirement (R1–R5) directly to its corresponding KPI and SQL analytical query using the `dw_eva_agricola` schema, the requested section is provided below:

### 16.1. R1 — Temporal Evolution of Production & Yield
*   **Analytical Requirement & Business Context:** Analyze how crop production and yield have evolved in Colombia between 2019 and 2025 to identify growth or decline trends.
*   **Associated KPI:** National Production Growth Rate & Average Yield
    $$\text{Yield} = \frac{\sum \text{Production (Ton)}}{\sum \text{Harvested Area (Ha)}}$$
*   **SQL Analytical Query:**
	```sql
	SELECT 
	    t.anio, 
	    SUM(f.produccion) AS total_produccion_ton, 
	    SUM(f.area_cosechada) AS total_area_cosechada_ha, 
		    ROUND(SUM(f.produccion) / NULLIF(SUM(f.area_cosechada), 0), 2) AS rendimiento_promedio_ton_ha 
		FROM fact_produccion_agricola f 
		JOIN dim_tiempo t ON f.sk_tiempo = t.sk_tiempo 
		GROUP BY t.anio 
		ORDER BY t.anio;
	```
### 16.2. R2 — Territorial Productivity Gaps
*   **Analytical Requirement & Business Context:** Compare agricultural performance across departments and municipalities to detect regional efficiency disparities.
*   **Associated KPI:** Regional Agricultural Yield
    $$\text{Yield}_{m} = \frac{\sum \text{Production}_{m}}{\sum \text{Harvested Area}_{m}}$$
*   **SQL Analytical Query:**
	```sql
	SELECT 
    g.departamento, 
    g.municipio, 
    c.cultivo, 
    SUM(f.produccion) AS total_produccion_ton, 
    SUM(f.area_cosechada) AS total_area_cosechada_ha, 
    ROUND(SUM(f.produccion) / NULLIF(SUM(f.area_cosechada), 0), 2) AS rendimiento_ton_ha 
	FROM fact_produccion_agricola f 
	JOIN dim_geografia g ON f.sk_geografia = g.sk_geografia 
	JOIN dim_cultivo c ON f.sk_cultivo = c.sk_cultivo 
	GROUP BY g.departamento, g.municipio, c.cultivo 
	HAVING SUM(f.area_cosechada) > 0 
	ORDER BY rendimiento_ton_ha DESC;
	```
### 16.3. R3 — Land Utilization Efficiency
*   **Analytical Requirement & Business Context:** Evaluate cases where high planted or harvested area does not translate proportionally into high production.
*   **Associated KPI:** Harvest Success Rate & Yield Efficiency
    $$\text{Harvest Ratio} = \frac{\sum \text{Harvested Area}}{\sum \text{Planted Area}}$$
*   **SQL Analytical Query:**
	```sql
	SELECT 
    g.departamento, 
    c.cultivo, 
    SUM(f.area_sembrada) AS total_sembrada_ha, 
    SUM(f.area_cosechada) AS total_cosechada_ha, 
    SUM(f.produccion) AS total_produccion_ton, 
	    ROUND((SUM(f.area_cosechada) / NULLIF(SUM(f.area_sembrada), 0)) * 100, 2) AS porcentaje_cosechado 
	FROM fact_produccion_agricola f 
	JOIN dim_geografia g ON f.sk_geografia = g.sk_geografia 
	JOIN dim_cultivo c ON f.sk_cultivo = c.sk_cultivo 
	GROUP BY g.departamento, c.cultivo 
	ORDER BY total_sembrada_ha DESC;
	```
### 16.4. R4 — Strategic Crop Ranking
*   **Analytical Requirement & Business Context:** Identify crops concentrating the highest total production volume and compare their relative yield levels.
*   **Associated KPI:** Crop Production Share & Yield Ranking
    $$\text{Volume Share} = \frac{\text{Production}_{c}}{\text{Total Production}}$$
*   **SQL Analytical Query:**
	```sqL
	SELECT 
    c.grupo_cultivo, 
    c.cultivo, 
    SUM(f.produccion) AS total_produccion_ton, 
    SUM(f.area_cosechada) AS total_cosechada_ha, 
    ROUND(SUM(f.produccion) / NULLIF(SUM(f.area_cosechada), 0), 2) AS rendimiento_ton_ha 
	FROM fact_produccion_agricola f 
	JOIN dim_cultivo c ON f.sk_cultivo = c.sk_cultivo 
	GROUP BY c.grupo_cultivo, c.cultivo 
	ORDER BY total_produccion_ton DESC;
	```
### 16.5. R5 — Crop Cycle & Period Structural Performance
*   **Analytical Requirement & Business Context:** Compare performance metrics between temporary and permanent crops across annual vs. semester periods.
*   **Associated KPI:** Cycle Performance Disparity Index (Metric breakdown grouped by `ciclo_cultivo` and `tipo_periodo`).
*   **SQL Analytical Query:**
	```sqL
	SELECT 
    c.ciclo_cultivo, 
    t.tipo_periodo, 
    t.anio, 
    SUM(f.area_sembrada) AS total_sembrada_ha, 
    SUM(f.area_cosechada) AS total_cosechada_ha, 
    SUM(f.produccion) AS total_produccion_ton, 
    ROUND(SUM(f.produccion) / NULLIF(SUM(f.area_cosechada), 0), 2) AS 	rendimiento_ton_ha 
	FROM fact_produccion_agricola f 
	JOIN dim_cultivo c ON f.sk_cultivo = c.sk_cultivo 
	JOIN dim_tiempo t ON f.sk_tiempo = t.sk_tiempo 
	GROUP BY c.ciclo_cultivo, t.tipo_periodo, t.anio 
	ORDER BY c.ciclo_cultivo, t.tipo_periodo, t.anio;
	```

# 18. Findings and Analytical Interpretation

## 18.1. Finding 1
The temporal analysis reveals that agricultural production and yield must be interpreted jointly across the 2019–2025 period rather than through production volume alone. The EVA dataset allows the dashboard to identify changes in total production, harvested area, and yield over time, while the crop-cycle perspective highlights structural differences between temporary and permanent crops. Temporary crops generally represent production systems with shorter production cycles and stronger dependence on the timing of sowing and harvesting, whereas permanent crops are associated with longer-term production structures and therefore follow a different temporal behavior.

A critical consideration in the interpretation of R1 and R5 is the methodological change introduced in 2022 for temporary crops. Before 2022, the corresponding area variables were related to sowing, while from 2022 onward they represent effective harvesting. Consequently, variations observed around the 2021–2022 transition cannot be interpreted exclusively as real changes in agricultural productivity. Part of the observed change may result from the methodological adjustment in how agricultural activity was recorded and reported.

For this reason, the dashboard is designed to distinguish annual and semiannual periods and to provide temporal filters that allow users to analyze the complete 2019–2025 series while recognizing the methodological break. This treatment improves analytical reliability by preventing direct comparisons from being interpreted without considering the underlying change in measurement criteria. The main insight from R1 and R5 is therefore that Colombian agricultural performance presents both temporal and structural variability, and that production trends must be evaluated together with yield, crop cycle, period type, and the methodological context of the data.

## 18.2. Finding 2
The geographic analysis demonstrates the importance of territorial disaggregation when evaluating agricultural productivity in Colombia. The EVA dataset covers departments and municipalities with substantially different agricultural conditions, allowing the dashboard to identify productivity gaps that may not be visible in national aggregates. For R2, comparing departments and municipalities by yield makes it possible to distinguish territories with relatively higher agricultural efficiency from those where production is lower relative to the harvested area.

The analysis also supports the interpretation of land-use efficiency required by R3. A larger agricultural area does not necessarily imply proportionally higher production. Territories may report extensive planted or harvested areas while achieving comparatively lower output per hectare, whereas other territories may obtain higher production from smaller cultivated areas. This relationship is particularly relevant because it shifts the analytical focus from the absolute amount of land used toward the efficiency with which that land is converted into agricultural output.

The Power BI dashboard makes these differences visible through territorial rankings and comparative views, allowing users to move from department-level analysis to municipality-level detail. This supports institutional stakeholders such as the Ministry of Agriculture and Rural Development and UPRA in identifying areas that may warrant further investigation, technical assistance, or more detailed territorial analysis. The finding should not be interpreted as proof that low yield is caused by inefficient land management, since EVA alone does not capture all explanatory factors such as climate, soil quality, infrastructure, technology, inputs, or market conditions. Instead, the dashboard identifies where productivity gaps occur and where additional analysis may be most valuable.

## 18.3. Finding 3
The crop analysis confirms the strategic importance of identifying which agricultural products concentrate production and how their yields behave across territories and periods. R4 allows the dashboard to rank crops according to production and to compare those results with harvested area and yield. This perspective is relevant to the ODS 2 objective because crops with significant production volumes can have a greater influence on the overall availability of agricultural products and therefore deserve closer monitoring in terms of productivity and territorial concentration.

At the same time, the analysis requires careful treatment of structural anomalies in the source data. One of the most important behaviors observed after 2022 is the appearance of cases in which harvested area exceeds planted area. This pattern should not automatically be interpreted as a physical inconsistency in agricultural activity. It is consistent with the methodological change affecting temporary crops, where the definition and reporting of area variables changed from sowing-oriented measurements before 2022 to effective harvest-oriented measurements from 2022 onward.

Accordingly, the dashboard and its analytical interpretation treat these observations as a data-structure and methodological issue rather than an automatic indication of erroneous records. This distinction is essential for R4 and for any strategic comparison involving production, area, or yield across the full 2019–2025 period. The resulting insight is that dominant crops can provide a useful perspective on national agricultural relevance, but their interpretation must remain sensitive to temporal comparability, reporting definitions, and the methodological characteristics of EVA.

# 19. Limitations and Assumptions

## 19.1. Limitations
The analytical scope and interpretation of the Data Warehouse and its associated Business Intelligence dashboard are subject to several inherent limitations arising from the source data and methodological constraints:

*   **Absence of Exogenous Explanatory Variables:** The EVA dataset contains information strictly limited to geographic, crop classification, temporal, and surface/production metrics (`area_sembrada`, `area_cosechada`, `produccion`, `rendimiento`). It does not capture external driving factors such as soil quality, climate variability, water availability, technological inputs, fertilizer usage, socio-economic conditions, or local infrastructure. Consequently, identified productivity gaps (R2, R3) describe where efficiency differences occur, but cannot definitively prove why they happen.
*   **Methodological Structural Break (2022):** A significant change in reporting methodology occurred around 2022, particularly affecting temporary crops. This shift resulted in a massive appearance of records where harvested area exceeds planted area and introduced a temporal discontinuity. Direct historical comparisons between the pre-2022 (2019–2021) and post-2022 (2022–2025) periods must be interpreted with caution, as part of the observed variation stems from reporting criteria changes rather than actual shifts in agricultural productivity.
*   **Absence of Daily or Sub-Annual Granularity:** The temporal dimension is bound strictly to annual observations and semestral periods (A and B). It lacks daily, monthly, or exact harvest-date tracking, preventing fine-grained intra-semester seasonality analysis.
*   **Data Quality and Reporting Nature:** As an institutional statistical compilation sourced from regional estimates and administrative reporting rather than precise census metering, anomalies such as zero-value patterns (e.g., planted area with zero harvest) reflect the complexities of field reporting. While preserved as valid real-world observations, they remain subject to estimation errors inherent to regional agricultural data collection.


## 19.2. Assumptions
To establish a coherent analytical framework and ensure the feasibility of the dimensional model and ETL pipeline, the following baseline assumptions were adopted:

*   **Validity of Source Identifiers:** It is assumed that the DANE geographic codes (`codigo_departamento`, `codigo_municipio`) and crop identification codes (`codigo_cultivo`) serve as stable and reliable business keys for entity resolution, outperforming raw text names which are subject to spelling variations and code-sharing across municipalities.
*   **Preservation of Source Values:** It is assumed that zero values and anomalies (such as harvested areas exceeding planted areas post-2022) represent valid operational or methodological phenomena rather than corrupt data entry errors. Therefore, these values are intentionally preserved without automated mathematical correction or deletion.
*   **Independence of Annual Records:** It is assumed that annual reporting periods represent distinct institutional observations rather than mathematical aggregates of semester periods (A + B). Consequently, annual data is treated as an independent temporal entity within `dim_tiempo` and is not auto-calculated inside the ETL pipeline.
*   **Institutional Analytical Relevance:** It is assumed that structuring the data around the selected performance indicators (production volume, harvested area, and yield) provides sufficient analytical depth to support decision-making for institutional stakeholders (MADR, UPRA) regarding the availability and stability dimensions of SDG 2 (Zero Hunger).

# 20. Reproducibility and Execution

## 20.1. Prerequisites

To fully reproduce the ETL pipeline, set up the Data Warehouse, and interact with the Business Intelligence dashboard, ensure the following software and tools are installed on your local environment:
-   **Python 3.9 or higher** (with pip package manager)

-   **MySQL Server 8.0** (or compatible MySQL instance supporting InnoDB engine and utf8mb4 collation)

-   **Power BI Desktop** (for viewing and interacting with the `.pbix` dashboard file)
-   **Git** (for cloning the repository)

Required Python libraries include `pandas`, `sqlalchemy`, and `pymysql`.

## 20.2. Installation

1.  Clone the repository to your local machine and navigate into the project root directory:

    ```
    git clone <repository-url>
    cd <repository-directory>
    
    ```  
2.  Create and activate a virtual environment:
    ```
    python -m venv venv
    # On Windows:
    venv\Scripts\activate
    # On macOS/Linux:
    source venv/bin/activate
    
    ```
3.  Install the required dependencies
    
    ```
    pip install pandas sqlalchemy pymysql
    
    ```
4.  Configure your MySQL database credentials as environment variables in your system or through a local execution script setup:
    
    ```
    export MYSQL_HOST="localhost"
    export MYSQL_PORT="3306"
    export MYSQL_USER="root"
    export MYSQL_PASSWORD="your_password"
    
    ```
    
    _(Note: The default connection uses user `root` and password `root` as configured in the loading modules, or can be overridden via environment variables)._
  
## 20.3. Data Acquisition

1.  Ensure the official raw dataset file (`Evaluaciones_Agropecuarias_Municipales_–_EVA._2019_-_2025._Base_Agrícola_20260905.csv`) is placed inside the `data/raw/` directory.
2.  Alternatively, run the extraction module to verify and log raw data ingestion:
    
    ```
    python src/extraction/extraccion.py
    
    ```
## 20.4. Data Profiling Execution
Execute the exploratory data analysis and statistical profiling scripts to generate diagnostic reports inside the `outputs/exploracion/` directory:

```
python src/EDA/01_exploracion_inicial.py
python src/EDA/02_perfilamiento_dataset.py
python src/EDA/03_analisis_semantico.py
python src/EDA/03_1_investigacion_reglas.py
python src/EDA/03_2_validacion_hipotesis.py

```
## 20.5. ETL Pipeline Execution

Run the transformation and staging validation scripts to process raw data, handle encoding and decimal conversions, and generate the structured staging file:
```
python src/staging/transformacion_staging.py
python src/staging/validacion_staging.py
python src/staging/perfilamiento_fisico_staging.py
python src/staging/validacion_historica_dimensiones.py

```
This process validates the structural integrity and creates `data/staging/eva_agricola_staging.csv`.

## 20.6. Data Warehouse Setup

1.  Execute the Data Definition Language (DDL) script located in `sql/` to create the target database (`dw_eva_agricola`) and its tables (`dim_geografia`, `dim_cultivo`, `dim_tiempo`, `fact_produccion_agricola`):
   
    ```
    mysql -u root -p < sql/01_crear_esquema_dw.sql
    
    ```
2.  Execute the main orchestration and loading script to populate the Data Warehouse from the staging layer, generate surrogate keys, load dimensions, and stream the fact table:
    
    ```
    python src/load/carga_dw.py
    
    ```
## 20.7. Analytical Queries Execution

To run the analytical queries answering the business requirements (R1–R5), execute the SQL script located in the `sql/` directory against the `dw_eva_agricola` database:
```
mysql -u root -p dw_eva_agricola < sql/consultas.sql

```	
## 20.8. Dashboard Connection and Update
1.  Navigate to the **`dashboard/`** directory and open the Power BI project file (`.pbix`) using Power BI Desktop.
2.  If prompted, update the MySQL database connection parameters (Server: `localhost`, Database: `dw_eva_agricola`) to match your local MySQL credentials.
3.  Click **Refresh** in Power BI Desktop to pull the latest transformed records from the MySQL Data Warehouse into the Power BI semantic model.
4.  Export updated visual artifacts or screenshots of the dashboard and store them inside the **`assets/`** directory for documentation and README referencing.
